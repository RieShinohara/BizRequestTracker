# 03 API の設計

要件定義とプロトタイプのあと、バックエンドを作る前に、API の設計書（[api-design.md](../docs/api-design.md)）を書いた。そのときに学んだこと。

## 1. API とは何か
- 画面（Vue）が、バックエンド（FastAPI）に「この依頼の一覧をください」「このステータスを変えてください」と頼むときの、**決まった窓口**
- 窓口は、**URL** と **やりたいこと**（取得 `GET`、追加 `POST`、一部の更新 `PATCH`、入れ替え `PUT`、削除 `DELETE`）の組み合わせで表す
- **REST**：表（依頼、依頼者、カテゴリー…）ごとに窓口を作る、という作り方。例：`GET /api/requests`（依頼の一覧）、`PATCH /api/requests/9`（依頼 9 の更新）
- 先に設計書を書く理由：画面とバックエンドを、別々の PR で作るため。窓口の約束が決まっていれば、画面側もバックエンド側も迷わない

## 2. 決めたことと、その理由
| 決めたこと | 理由 |
|---|---|
| 検索・絞り込み・並び替えは**サーバー側**。条件は `?q=通関&qms=true&sort=due_on` のように URL に付ける | 窓口が増えない。依頼が増えても遅くなりにくい。API の入力と出力として、テストで確かめられる |
| 優先度やステータスの並び順は、サーバーが**決まった順番**で並べる | 「急ぎ・高・中・低」は、文字の五十音順ではないため |
| 進み具合（3/6）と期限の色は、**サーバーが計算**して返す | 祝日と会社の休みの判定が、サーバーの1か所にまとまる。テストしやすい |
| 依頼の更新は、**変えたい項目だけ送る** `PATCH` | 一覧からステータスだけ変えるときに、他の項目を古い値で上書きしないため |
| ドラッグ＆ドロップの保存は、**並び全体**を送る `PUT /api/requests/order` | サーバーは、受け取った順に番号を振り直すだけ。単純で、間違えにくい |
| 新しい依頼者は、先に登録してから、番号（`id`）で依頼を保存する（2段階） | 依頼の窓口が単純になる。名前の重複は、DB の制約で守れる |
| エラーは **404（見つからない）・409（今の状態ではできない）・422（入力が正しくない）** | 世界共通の番号に合わせると、画面が番号を見て動きを変えられる。理由の文は `{"detail": "..."}` |

## 3. ユースケースを読んで、設計の見落としに気づいた
### 何があったか
- 最初は、「テンプレートを入れる」専用の窓口 `POST /api/requests/9/checklist-items/from-template` を提案した
- でも、ユースケースを読み直すと、2つの問題があった
  1. **まだ保存していない新しい依頼**（UC-1）でもチェックリストを作れるので、依頼の番号がまだない
  2. チェックリストの変更は、項目ごとではなく、**「保存」を押したときにまとめて反映**される（UC-2、UC-7、UC-8）
- そこで、**依頼の保存に、チェックリスト全体を入れて送る**形に変えた。チェック項目だけの窓口と、テンプレート専用の窓口は、作らない

### 教訓
- **設計は、ユースケース（操作の流れ）と照らして確かめる**。窓口だけを見ると正しそうでも、実際の操作の順番と合わないことがある
- 気づいたら、**正直に伝えて、設計を直す**。直す前に、変わる点（作らなくなる窓口、画面側が担当すること）を、ユーザーに説明して確認した
- 全部を保存した状態か、していない状態かの、**中途半端がない**ところも、まとめて保存する形の良い点

## 4. 進め方で学んだこと
- **質問は1つずつ**。選択肢を表で比べて、おすすめと理由を添えると、決めやすい
- 用語（API、REST、サーバー側、画面側）は、たとえ話で説明する。例：レストランの注文に「魚料理だけ」と条件を付ける
- 決めたことと、**Claude Code が補った点**を、設計書の中で分けて書く（表の「決定」と「要確認」）。補った点は、PR のレビューで確認してもらう
- 決まったことが、ほかの文書の「未決」に関わるときは、同じ PR で直す（確認先の候補の置き場所を、設定ファイルに決めた）

3. 機能ごとの API（窓口ごとに、Issue と PR を分ける）。そのあとに、画面（本番）
