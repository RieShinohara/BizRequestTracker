# 画面：エラーの理由を出す・通信コードを整理する

品質チェックの F1・F7（[docs/quality-review.md](../docs/quality-review.md)）への対応。依頼の保存などに失敗すると、どの場合も同じ文（「保存できませんでした。入力を確かめて…」）が出ていた。API は、理由を返しているのに、画面が捨てていた。

## 直したこと
| 状況 | 前 | 後 |
|---|---|---|
| 並びを保存するとき、別の画面で依頼が増えていた（409） | 「並びを保存できませんでした。一覧を取り直しました。もう一度…」 | API の理由「一覧が古くなっています。開き直してください」＋「（一覧を取り直しました）」 |
| 依頼が、すでに完全に削除されていた（404） | 「保存できませんでした。入力を確かめて…」 | 「依頼が見つかりません」 |
| タイトルが 201 文字以上 | 「保存できませんでした。入力を確かめて…」（API の 422 の理由は、人が読めない配列） | 保存の前に、「タイトルは200文字までです」 |
| 通信のコード | `getJson`・`sendJson` と、直書きの3つの関数の、2通り | `getJson`・`send`・`sendJson` の3つに、まとめた |

## 作ったもの・変えたもの
| 場所 | 中身 |
|---|---|
| `frontend/src/api.ts` | 通信の入口を3つにまとめ、すべて失敗したら、理由つきの `ApiError` を投げる。理由を取り出す `apiErrorMessage`（カテゴリー管理と共通） |
| `frontend/src/requestForm.ts` | 文字数の上限（`MAX_LENGTH`）と、保存の前の検査（`validateForm`） |
| `App.vue`・`RequestDialog.vue` | ステータス変更、並びの保存、保存・アーカイブ・削除の失敗で、API の理由を出す |
| テスト | `api.test.ts`・`requestForm.test.ts`（合計 151 件） |

## 学んだこと
- **通信の入口は、1つにする。** 同じ「送って、失敗したら例外」の処理を、関数ごとに書いていた（直書きが3か所）。そのため、カテゴリー管理で作った「理由つきのエラー」が、依頼まわりでは使えなかった。入口を3つ（取得・送信・送信して返事を受け取る）にまとめると、**すべての API 呼び出しで、同じ形のエラー**になり、直すのも1か所で済む。動作を変えない整理は、**前後でテストが同じ結果になること**で確かめる（既存のテストは、書き換えずに通った）
- **画面の「親切」と、API の「守り」は、役割が別。** 文字数の上限は、API が、守りの本番（422 で断る）。画面は、API に送る**前**に、同じ上限を調べて、**どの項目が、何文字までか**を、人が読める文で知らせる。API の 422 の `detail` は、機械向けの配列なので、そのままは出せない
- **上限は、実際に送る形で数える。** 確認先は、「確認待ち」のときだけ送る。だから、それ以外のステータスでは、確認先が長くても、止めない。前後の空白は、送るときに取るので、数えない。「送らないもの」や「取る部分」まで検査すると、**本当は送れる入力を、止めてしまう**
- **理由が読めないときの逃げ道を、必ず用意する。** `apiErrorMessage(error, 操作ごとの文)` は、API の理由（文字）があれば、それを使い、なければ、操作ごとの文を使う。つながらない（ネットワークの失敗）ときは、API の理由がないので、これまでの文になる。API の理由に頼り切らない
- **名前の衝突に注意する。** 部品の中に、`errorMessage` という変数があった。同じ名前の関数を取り込むと、衝突する。関数のほうを `apiErrorMessage` にした。**名前は、何をするかが、分かるように付ける**
- **手順を作る側も、間違える。** ユーザーに「別のタブでアーカイブして、完全に削除して、保存する」と頼んだとき、アーカイブだけで止まった。アーカイブ中の依頼は、まだ存在するので、保存は成功する（正しい動き）。「404 になる条件」を、手順に正確に書く。再現が大変な経路は、**自動テスト**（`updateRequest` が 404 の理由を取り出す）でも確かめた。そのあと、ユーザーが、**完全に削除してから保存**する手順で、画面でも「依頼が見つかりません」が出ることを確認した（**自動テストと、実際の画面の、両方で確かめられた**）

## 直さなかったこと
- 読み込みの失敗（一覧、詳細、候補）の文言は、そのまま。「読み込めませんでした」で、ほぼ足りるため（ユーザーと決定）
- 入力欄の文字数カウンター（`counter`）は、付けていない。見た目が変わるため。必要になったら、相談する
- 返事の型の読み替え（`as T`）は、そのまま。中身を調べる仕組み（型ガード）は、効果に比べて作業が大きい

## やってみよう
1. 「新しい依頼」を開き、タイトルに 201 文字以上を貼り付けて保存する。上限のメッセージを見る
2. `api.test.ts` の「依頼まわりの失敗は、API の理由つきの ApiError になる」を開き、422（detail が配列）のときだけ、`detail` が `null` になることを確かめる
