# 画面：アーカイブと完全な削除

## 作ったもの
| 場所 | 中身 |
|---|---|
| `frontend/src/components/RequestDialog.vue` | 下の段（左）に、「アーカイブ」（アーカイブ中は、「アーカイブ中」の印と、「元に戻す」「完全に削除」）。「完全に削除」は、確認のダイアログを出す。新しい依頼には、出さない |
| `frontend/src/api.ts` | `deleteRequest`（`DELETE /api/requests/{id}`）。アーカイブと元に戻すは、既存の `updateRequest` で `archived` だけを送る |
| `frontend/src/types.ts` | `RequestPatch` に `archived` を追加 |

アーカイブ・元に戻す・削除のあとは、モーダルを閉じて、一覧と件数を取り直す（保存のときと同じ流れ）。

## 学んだこと
- **「消さずに隠す」と「完全に消す」を分ける**：アーカイブは、`archived` の印を付けるだけで、データは残る（元に戻せる）。完全な削除は、元に戻せない。だから、削除の前に、確認のダイアログを必ず挟む。さらに API 側でも、アーカイブ中の依頼だけを消せるようにして（そうでないと 409）、画面の誤操作を二重に防いでいる
- **確認のダイアログに、何が起きるかを書く**：「元に戻せません」「チェックリストも一緒に消えます」と書く。「本当に削除しますか？」だけだと、何が失われるかが分からない
- **ボタンは、状態で出し分ける**：同じ場所に、「アーカイブ」（通常）と、「元に戻す」「完全に削除」（アーカイブ中）を、`v-if` で切り替える。アーカイブ中でない依頼に、「完全に削除」は出さない（誤って押せない）
- **通信中は、ボタンを押せなくする**：アーカイブや削除の通信中に、別のボタンを押せると、二重に送ってしまう。`working` の間は、`disabled` にした
- **変数は、使う前に宣言する**：`watch` に `immediate`（最初に1回すぐ動く）を付けると、その中で使う変数が、`watch` より後ろで宣言されていると、起動時にエラーになる（`const` は、宣言より前に使えない）。削除の確認用の変数を、上のほうにまとめた
- **API の動きを、画面とは別に確かめる**：アーカイブ前の削除が 409、アーカイブすると件数が減る、元に戻すと戻る、アーカイブ中の削除が 204、削除後は 404。画面を通さずに確かめると、問題が API と画面のどちらにあるかを、切り分けやすい

## 要件にない、私（Claude Code）が決めた点
- アーカイブ・元に戻すは、`archived` **だけ**を送る。モーダルで直している途中の内容は、保存されない（アーカイブの前に直したいときは、先に「保存」を押す）
- アーカイブ中の依頼のモーダルには、「アーカイブ中」の印を出した
- 削除に失敗したときは、確認のダイアログを閉じて、モーダルの中に、メッセージを出す

## 確認が必要なこと
- ブラウザで、見た目と動きを確認する（私は、ブラウザを操作できない）
- 本物の API で、アーカイブ・元に戻す・削除と、件数・一覧への反映を確認した（確認用の依頼は、削除した）
