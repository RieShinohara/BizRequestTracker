# 依頼の API（追加・1件取得・更新・削除）

## 作ったもの
| 窓口 | 内容 |
|---|---|
| `POST /api/requests` | 依頼の追加（201）。チェックリストも一緒に保存する |
| `GET /api/requests/{id}` | 依頼1件（依頼者の内線番号、チェックリストの中身、進み具合つき） |
| `PATCH /api/requests/{id}` | 送った項目だけ変更。アーカイブの切り替えも、これで行う |
| `DELETE /api/requests/{id}` | アーカイブ中の依頼だけ削除（204）。そうでなければ 409 |

場所は `backend/app/routers/requests.py`。テストは `backend/tests/test_requests_api.py`（37件）。仕様は [docs/api-design.md](../docs/api-design.md) の「3」。

依頼の API は大きいので、3つの Issue に分けた。今回は①。②一覧と手動の並び（検索・並び替え・期限の色）、③件数と確認先の候補は、このあと。

## 学んだこと
- **許される値は、API の入口で確認する**：ステータスと優先度は、DB には文字で入れている（`CHECK` 制約なし）。そのかわり、Pydantic の `Literal["未着手", "作業中", ...]` で、決められた値以外を 422 で断る。値を増やすときは、`schemas.py` の1か所を直す
- **PATCH で、null を送れる項目と、送れない項目**：`description` と `confirm_to` は、null を送って「消す」ことができる。タイトルや期限などの必須の項目に null を送ると 422
- **確認先（`confirm_to`）は、ステータスが変わっても消さない**：「確認待ち」から「作業中」に戻しても残る。画面で隠すだけ（data-model.md の決めごと）
- **チェックリストは、全体を入れ替える**：`checklist_items` を送ると、送った一覧がそのままチェックリストになる。送らなければ、そのまま。空の一覧を送ると、全部消える
- **進み具合は、保存せず、その都度数える**：`checklist_done`（`done` が true の数）と `checklist_total`（全部の数）は、返すときに数える。保存すると、チェックを付けたときに2か所を直す必要があり、ずれる元になる
- **「いちばん上」の作り方**：手動の並びは `sort_order` の小さい順。新しい依頼は、今ある最小の番号より1つ小さい番号（0、-1、…）にする。ほかの依頼の番号を、書き換えずに済む
- **削除の条件はサーバーが守る**：画面が「アーカイブ中だけ削除ボタンを出す」としても、API 自身が、アーカイブ中でなければ 409 で断る。画面を通らない呼び出しでも、安全にするため
- **存在しない相手の指定は 422**：依頼者やカテゴリーの番号が、登録されていなければ 422。「その依頼」が見つからない（404）のとは、区別した

## 要件にない、私（Claude Code）が決めた点
- 存在しない依頼者・カテゴリーの番号を送ったときは、404 ではなく 422（入力が正しくない）にした
- `PATCH` の返事は、設計書どおり更新後の内容。`description` は1万文字まで、`confirm_to` は100文字まで、タイトルは200文字まで
- `confirm_to` を空の文字で送ったら、「なし」（null）として保存する
- **`due_level`（期限の色）は、この Issue では返していない。** 設計書では、一覧と詳細に入るが、営業日の計算に祝日ライブラリが必要なので、②で作る。そのとき、詳細にも入れる

## つまずいたこと
- **日本語を含む SQL を PowerShell から渡すと、文字コードが合わず、`WHERE name='…'` が一致しなかった**：試験データが消えずに残った。番号（`WHERE id=3`）で指定して消した。日本語で絞るときは、`--default-character-set=utf8mb4` を付ける
