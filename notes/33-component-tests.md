# 画面の部品のテスト（Vue の部品を、テストの中で動かす）

品質チェックの F4・F10（[docs/quality-review.md](../docs/quality-review.md)）への対応。道具の追加の2つ目。これまでの画面のテスト（151 件）は、部品から切り離した**関数だけ**のテストで、Vue の部品（詳細モーダル、カテゴリー管理など）を動かすテストがなかった。

## 作ったもの
| 場所 | 中身 |
|---|---|
| `frontend/src/test-utils/mount.ts` | 部品を、Vuetify つきで描く道具。jsdom にない機能の補い |
| `frontend/src/components/RequestDialog.test.ts` | 詳細モーダルのテスト（13 件）：開く／閉じる確認（F2）／保存／API の理由の表示（F1）／新しい依頼 |
| `frontend/src/components/CategoryDialog.test.ts` | カテゴリー管理のテスト（13 件）：一覧／削除できるか／追加／名前の変更／エラー |
| `frontend/vite.config.ts` | Vuetify を、テストの道具に読ませる設定 |
| 入れた部品 | `@vue/test-utils` 2.5.1、`jsdom` 30.1.3（どちらも版を固定） |

画面のテストは、合計 177 件（元の 151 件＋26 件）。

## 学んだこと
- **関数のテストと、部品のテストは、守るものが違う。** 関数のテストは、「この入力なら、この答え」。部品のテストは、「ボタンを押すと、画面がこう変わり、API がこう呼ばれる」。**画面を操作する流れ**を、機械が確かめる。今回、「変更中は、閉じない」「API の理由が、エラー欄に出る」「使われているカテゴリーは、削除ボタンが押せない」が、テストで守られた
- **ブラウザの代わり（jsdom）が要る。** Vue の部品は、ブラウザの上で動く前提で作られている。テストの中でも、ブラウザに似た環境が要る。それが jsdom。**部品のテストのファイルだけ**、先頭に `// @vitest-environment jsdom` と書く。ほかのテスト（関数だけ）は、軽い環境（node）のまま。速さを保つため
- **jsdom には、ないものがある。** Vuetify が使う `ResizeObserver` と `visualViewport` が、jsdom にない。最初は、`visualViewport is not defined` で、13 件すべてが失敗した。**何もしない代用品**で補った（`test-utils/mount.ts`）。本物の画面の位置の計算は、テストの対象ではないので、固定の大きさを返す代用品で足りる
- **通信（API）は、本物を呼ばない。** `vi.mock('../api', …)` で、API の関数を、決めた返事を返す代用品にする。成功も、失敗（`ApiError`）も、思いどおりに作れる。`importOriginal` で、`ApiError` や `apiErrorMessage` は、**本物のまま**残す。何でも代用品にすると、「本物の動き」を、テストしなくなる
- **モーダルは、画面の外側に描かれる。** `v-dialog` は、内容を `document.body` の外側（teleport）に出す。部品の中を探しても、見つからない。`document.body` から探す（`byTestId`）。使い終わったら、`unmount()` し、`document.body` を空にする（テスト同士が、影響しあわないように）
- **`v-combobox`（選ぶか、打つ入力欄）は、文字を打っただけでは、値が決まらない。** Enter や、フォーカスが外れたときに決まる。jsdom では、その動きを再現しにくい。テストでは、部品に「この名前が選ばれた」という通知（`update:modelValue`）を、直接送った。**テストしにくい所は、無理に本物の操作を真似せず、部品の入口を使う**
- **テストが通るだけでは、検査が働いているとは限らない。** 「わざと壊して、失敗するか」を確かめた（変異テストの、手作業版）。①変更中でも閉じる設定（`persistent`）を、常に `false` にする → 2 件失敗 ②API の理由を捨てる → 1 件失敗 ③使われているカテゴリーも、削除できるようにする → 1 件失敗。**3 つとも、検出できた**。壊した変更は、すぐ元に戻した
- **テストも、型の検査（`vue-tsc`）の対象。** `npm run build` が、テストのファイルも、型検査する。IDE の赤い波線と、ビルドの結果は、ずれることがある（`import` を足す前の古い表示）。**最後は、ビルドで確かめる**
- **`npm audit` の指摘が、4 件増えた。** `@vue/test-utils` が連れてくる `js-beautify` → `editorconfig` → `glob` → `minimatch` の鎖。以前からある ESLint まわりと、同じ種類（`minimatch` の処理が重くなる問題。中程度）。**テスト・開発用だけで、本番に入る部品は 0 件**。直すには、大きな更新（`--force`）が要る。直さない（見直す条件：本番の部品に出たとき）
- **版の選び方。** `jsdom` の最新（31.0.0）は、公開から2日で、避けた。公開から2週間以上たった 30.1.3 を選び、`^` を付けずに固定した（版が勝手に上がらない）

## 守れていないこと（正直に）
- **本物のキー操作**：Esc キーや、枠の外のクリックで、本当に閉じないかは、テストしていない。「閉じない設定（`persistent`）になっている」ことを、確かめた。実際の動きは、ブラウザで確かめた（F2 のとき）
- **見た目と、フォーカスの枠**：色・配置・Tab の位置の戻りは、テストできない（jsdom は、描画しない）
- **残りの部品**：一覧（`RequestTable`）、ステータス変更、テンプレート編集、`App.vue` は、まだ。必要になったら足す（ユーザーと決定）

## やってみよう
1. `frontend/` で、`npm.cmd run test` を実行して、177 件が通ることを確かめる
2. `RequestDialog.vue` の `:persistent="dirty"` を、一時的に `:persistent="false"` に書き換えて、テストを実行する。失敗することを確かめたら、`git checkout -- src/components/RequestDialog.vue` で元に戻す
3. `RequestDialog.test.ts` の `vi.mock` と、`mount.ts` の `ResizeObserverStub` を、読み比べる
