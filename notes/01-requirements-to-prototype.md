# 01 要件定義からプロトタイプまで

## 1. 今回の課題と、1本目との違い
- 課題：1本目のタスク管理アプリで習った工程を、**技術をすべて変えた新しいアプリ**で、もう一度やる（TypeScript だけは同じでよい）
- 作るもの：他部署からの制作依頼（通関書類、HP、取扱説明書、動画、AIアカウント発行など）を管理する、社内向けのアプリ

| | 1本目（タスク管理） | 2本目（今回） |
|---|---|---|
| サーバー | Java + Spring Boot | **Python + FastAPI** |
| データベース | PostgreSQL（Docker） | ~~SQLite（ファイル1つ）~~ → **MySQL（RDS）** に変更（[02](02-requirements-docs.md) を参照） |
| 画面 | React + Tailwind CSS | **Vue 3 + Vuetify** |
| ドラッグ＆ドロップ | dnd-kit | **vue-draggable-plus**（予定） |
| ビルドの道具 | Vite | Vite（メンターに確認して、同じものを使ってよいと確認済み） |

進める順番は同じ：**要件定義 → プロトタイプ → API → 画面 → 品質チェック → デプロイ（AWS）**。このノートは、プロトタイプまで。

## 2. 作業の1周（Issue → ブランチ → PR）
どんなに小さな作業でも、この順番で進めた。ルールの正本は、リポジトリ直下の [CLAUDE.md](../CLAUDE.md)。

```
1. Issue を作る       何をするかを、先に書く
2. ブランチを作る     gh issue develop 番号 --name 種類/番号-説明 --base main --checkout
3. 作業して、コミット
4. push して、PR を作る（本文に Closes #番号）
5. ユーザーが確認して、マージする
6. 手元の main を更新して、ブランチを整理（git pull → git branch -d → git fetch --prune）
```

- Issue と PR は、同じ連番を共有する。だから、Issue #5 のあとに作った PR が #6 になる。ブランチ名の番号は Issue に合わせる
- 今回から、**マージするとGitHub上のブランチが自動で消える**設定にした（リポジトリ設定 `delete_branch_on_merge`）。手元のブランチだけ、自分で消す

## 3. 要件定義：質問と回答を、小刻みに
上流の工程（何を作るかを決める）は、まとめて決めず、**質問 → 回答 → 文書に反映**を1つずつ進めた。

### 質問の形（Claude が出し、ユーザーが選ぶ）
- 選択肢を、**おすすめと理由つき**で出す
- Claude が付け足した提案は、「これは私の提案です」と明示して、採用するかを聞く
- 決まったことは、すぐ記録する（会話だけに残さない）

### 今回決めたことの例と、その理由
| 決めたこと | 理由 |
|---|---|
| 「承認待ち」を「**確認待ち**」に改名 | 確認する相手が、依頼ごとに違う（依頼者、薬事部、開発部…） |
| 確認待ちのとき「**確認先**」欄（選択式＋自由入力） | 「今、誰の返事を待っているか」が、一覧で分かる |
| 優先度は「**急ぎ・高・中・低**」の4段階 | 急ぎが別に欲しいという業務の実感から |
| 削除はせず「**アーカイブ**」で隠す。完全削除は、アーカイブ中のみ | うっかり消す事故を防ぐ。課題としても、削除は作る |
| 期限日は**必須**。期限の色分け（赤・オレンジ） | 空の期限は、並び替えや色分けが複雑になる |
| 「3日以内」は**営業日**で数える（土日祝＋会社の休み） | 実際の業務のカレンダーに合わせる |
| 依頼者は「選択式＋自由入力」、**部署は持たず内線番号だけ** | 兼任者が多く、連絡はチャットやメールが多い |
| カテゴリーは**使用中なら削除できない** | 依頼のカテゴリーが空になる事故を防ぐ。一番単純 |
| チェックリストの項目は**名前とチェックだけ** | 使う人が1人。期限や担当は、細かすぎる |

### 考え方（1本目から続くもの）
- **あいまいな言葉を、具体的にする**（例：「3日以内」→「3営業日以内」）
- **取り返しのつかない操作には、確認を入れる**（完全に削除）
- **「作らないもの」も決める**（ピン留め、ログイン）
- **公開リポジトリなので、実際の取引先や個人名は入れない**。サンプルは架空にする

## 4. データ設計（ER図）
DB に作る「表」を決めた。詳しくは [docs/data-model.md](../docs/data-model.md)。

| 表 | 持つもの |
|---|---|
| request（依頼） | タイトル、詳細、受付日、期限日、ステータス、優先度、確認先、QMS、アーカイブ、並び順 |
| requester（依頼者） | 名前、内線番号 |
| category（カテゴリー） | 名前 |
| template_item（テンプレート項目） | カテゴリー、項目名、順番 |
| checklist_item（チェック項目） | 依頼、項目名、チェック済みか、順番 |

### 設計の考え方
- **確認先は表にしない**：名前だけで、内線番号のような中身がないので、依頼の欄に文字で持つ（過去に使った文字を候補に出す）
- **テンプレートは、コピーして使う**：テンプレートを依頼に入れるとき、項目を**コピー**してチェック項目を作る。あとでテンプレートを直しても、すでにある依頼は変わらない
- **計算で出せるものは、保存しない**：進み具合（3/6）や期限の色は、その都度計算する
- **内線番号は、数字ではなく文字で持つ**：先頭の 0 が消えたり、「03-1234」のような区切りが入ったりするため

### 用語
| 用語 | 意味 |
|---|---|
| ER図 | 表と、表同士の関係を表す図。今回は Mermaid という書き方で、GitHub上で図として表示される |
| 主キー（PK） | 1行を区別するための番号（id） |
| 外部キー（FK） | 別の表の1行を指す番号（例：依頼の `requester_id` は、依頼者の `id` を指す） |
| 1対多 | 1つの依頼に、チェック項目が複数ある、という関係 |

## 5. 画面のプロトタイプ
使い捨ての試作を `prototype/` に作った。**API や DB にはつながない**。目的は、見た目と操作感を、本物に近い形で確かめること。

### 使った技術
| 技術 | 役割 |
|---|---|
| **Vue 3** | 画面の部品（コンポーネント）を作る道具。1本目の React にあたる |
| **TypeScript** | JavaScript に「型」を足したもの（1本目と同じ） |
| **Vuetify** | Vue 用の部品集。表、ボタン、モーダル、入力欄が、最初から用意されている |
| **Vite** | 開発中のサーバーと、本番用のビルドをする道具。React でも Vue でも使える |

### 動かし方
```
cd prototype
npm install      # 必要な部品をダウンロード（最初の1回）
npm run dev      # 開発サーバーを起動。http://localhost:5173
npm run build    # 型チェックと、本番用のビルド
```
- Windows の PowerShell では、`npm` が動かないことがある。そのときは `npm.cmd` を使う
- ポートは `vite.config.ts` で **5173 に固定**した（使用中なら、別のポートにせず、エラーで止める）

### ファイルの役割（`prototype/src/`）
| ファイル | 役割 |
|---|---|
| `main.ts` | 画面の起動と、Vuetify の設定（基調色など） |
| `App.vue` | 画面の全体（上のバー、件数、ボタン） |
| `components/RequestTable.vue` | 一覧の表 |
| `components/RequestDialog.vue` | 詳細のモーダル |
| `store.ts` | 画面が持つデータと、その変更 |
| `mockData.ts` | 架空の仮データとテンプレート |
| `dates.ts` | 日付、営業日、期限の色分けの計算 |
| `types.ts` | データの型（依頼、ステータスなど） |

### Vue の基本（1本目の React と比べて）
| 考え方 | Vue での書き方 |
|---|---|
| 1つのファイルに、見た目・動き・装飾をまとめる | `.vue` ファイル：`<template>`（見た目）、`<script>`（動き）、`<style>`（装飾） |
| 変わる値を持つ | `ref(値)`。読み書きは `.value`（テンプレートの中では不要） |
| 値から計算して出す | `computed(() => …)`。元の値が変わると、自動で再計算される |
| 入力欄と値をつなぐ | `v-model="値"` |
| 繰り返して並べる | `v-for="x in 一覧" :key="x.id"` |
| 条件で出し分ける | `v-if="条件"` |
| 親から子へ渡す／子から親へ知らせる | `defineProps`／`defineEmits` |

### 色の決め方（見た目の調整）
- 色は、**1か所（`main.ts`）で決めて、全体に効かせる**。部品ごとに色を直すと、あとで揃わなくなる
- 色を指定しない部品は、Vuetify の標準では黒くなる。`defaults` で、標準の色（primary）を決めた
- 青、ティール、インディゴ、ディープパープルを、**実際に画面に入れて見比べて**決めた。基調色はインディゴ
- 色同士の「近さ」も見る：基調色と「確認待ち」のラベルが近いと紛らわしい。ピンクは「赤っぽくて、せかされる感じ」がしたので、赤を抑えた赤紫にした
- 色は、**言葉の印象**でも選ぶ：「仕事では青系の印象が強い」

### 画面の動きで工夫したところ
- 一覧から、ステータスのラベルを押して**直接変更**できる。「確認待ち」にすると、確認先の入力欄が出る
- 画面の上に、ステータス別の件数と「急ぎ」の件数を出す。**優先度ごとの件数は出さない**（優先度は一覧の色で見えるため。二重の帯は、見る場所が増える）
- 数え方をそろえるのも大事：「急ぎ」は完了を除く（これからやる数）

## 6. つまずいたことと、教訓
| 出来事 | 原因 | 教訓 |
|---|---|---|
| 「React ではない」とだけ読んでいた | 記憶メモの要約が不正確だった | 課題の条件は、書かれた言葉のまま確認する。迷ったら、メンターに聞く |
| 画面のサーバーが、ブランチを切り替えたら壊れた | `prototype/` がまだ main になく、切り替えで**ファイルが消えた** | サーバーを動かしたまま、そのファイルを持たないブランチへ切り替えない |
| Issue 番号と PR 番号のずれ | Issue と PR は、同じ連番を共有する | ブランチ名は Issue 番号に合わせる。番号を確かめてから `gh issue develop` |
| 一部のコマンドが動かなかった | この PC に Python が入っていない | 本番の API を作る前に、Python の環境を用意する（次回） |
