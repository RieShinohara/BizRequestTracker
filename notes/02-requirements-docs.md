# 02 要件定義書を、項目別の文書に整える

プロトタイプまで終わったあと、1つのファイルに全部入っていた `requirements.md` を、1本目と同じ**項目別の文書**に組み替えた。そのときに学んだこと。

## 1. 文書の構成
`requirements.md` を**入口（ハブ）**にして、内容ごとに別の文書へリンクする。

| 文書 | 何が書いてあるか |
|---|---|
| [requirements.md](../docs/requirements.md) | 入口。目的、文書一覧、範囲の概要、**受け入れ条件**、未決 |
| [functional-requirements.md](../docs/functional-requirements.md) | 機能一覧：依頼の項目、ステータス、アーカイブ、期限の色分け、検索・並び替え、テンプレート |
| [use-cases.md](../docs/use-cases.md) | **ユースケース**：使う人の操作の流れ（12個） |
| [screen-design.md](../docs/screen-design.md) | 画面設計：一覧の列、件数、色、詳細モーダル |
| [non-functional-requirements.md](../docs/non-functional-requirements.md) | **非機能要件**：動作環境、保存、性能、バックアップ、セキュリティ、使いやすさ、権利 |
| [data-model.md](../docs/data-model.md) | データ設計：DB の表 |
| [tech-stack.md](../docs/tech-stack.md) | **技術スタック**：使う技術と、1本目との比較 |

### 用語
- **非機能要件**：「何ができるか」ではなく、「どんな条件で、どのくらいの品質で動くか」。例：対応するブラウザ、件数の目安、バックアップ
- **受け入れ条件**：完成かどうかを確かめる基準。「期限日が空では保存できない」のように、**できたか、できていないかが、はっきり分かる一文**で書く
- **ユースケース**：目的ごとに、事前条件・基本の流れ・例外の流れ・補足を書く。プロトタイプの動きと見比べて書くと、食い違いが見つかる

## 2. 進め方で学んだこと
- **振り分けと追加は、別の PR にする**。最初の PR は「内容を増やさない振り分け」だけにした。途中で出た要望（ステータス順の並び替え）は、別の Issue にして、先の PR がマージされてから始めた（同じ文書を触るので、混ざらないように）
- **質問は1つずつ**。性能・容量は、「1か月に何件くらい？」と聞いてから、数字（通常300件、目安1,000件）を決めた。感覚で答えられる質問にすると、決めやすい
- **決まったことは、関係する文書をそろえて直す**。必須項目を決めたら、機能一覧、受け入れ条件、ユースケースを同時に直した。1か所だけ直すと、文書同士が食い違う
- **PR を出したあとにも、grep で確かめる**。「SQLite」と書いた所が2か所残っていた。見つけたら、同じブランチに足して push すれば、PR に反映される

## 3. 課題の条件を、書かれた言葉のまま確認する
### 何があったか
- CLAUDE.md には「SQLite は EC2 の中。RDS は使わない」と書いてあった
- でも、ユーザーが聞いていた課題の条件は「**Terraform の AWS 構成は EC2＋RDS のまま**」「DB も 1本目とは別のもの」だった
- ユーザーの「DB も AWS に乗せるのが課題だと思ってました」という質問で、食い違いに気づいた

### 分かったこと
- **SQLite は、RDS が対応していない**（RDS は MySQL、MariaDB、PostgreSQL、SQL Server、Oracle など、サーバーとして動く DB が対象）
- SQLite は「ファイル1つ」の DB なので、EC2 のディスクの中に置く形になる。EC2 を消す（destroy）と、データも消える
- 結果：DB は **MySQL（RDS）** にした。メンターの回答で、変えるのは言語とフレームワーク（Java・Spring Boot と React）、課題の条件により DB も別のもの、と整理した

### 教訓
- **古い決定は、書いてあっても、そのまま信じない**。課題の条件（正本）と照らして確かめる
- 迷ったら、メンターに聞く（今回は、その回答が決め手になった）
- ルールの文書（CLAUDE.md）は、PR を分けて直す。文書の食い違いは、早めに直す

## 4. 技術の選び方
| 選んだもの | 理由 |
|---|---|
| SQLAlchemy ＋ Alembic | Python で最も使われている DB の道具。テーブルの変更の履歴が残る。仕事で見る機会が多い |
| uv | Python 本体の導入、部品、仮想環境を、1つの道具で扱える。新しいプロジェクトで増えている |
| MySQL | 課題の条件を満たす。名前をよく聞く、実務で使われる DB |
| ESLint | 1本目の oxlint から変えた。Vue でも標準的に使われている |

- **作業用の道具**（Git・GitHub・GitHub Actions・Terraform・AWS）は、アプリの技術ではないので、1本目と同じでよい
- 技術は、**比較表**にすると、「変えたもの」「同じでよいもの」が一目で分かる

## 5. バックアップの考え方の変化
- SQLite のとき：DB ファイルを、手でコピーすればバックアップになる
- MySQL のとき：データが1つのファイルではないので、使えない。代わりに `mysqldump` で、データを1つのファイルに書き出す
- 画面の機能は作らず、**手順を README に書く**。機能を作るかどうかは、使う頻度と手間で決める
- 書き出したファイルには、実際のデータが入るので、**公開リポジトリにコミットしない**
