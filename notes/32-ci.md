# CI（GitHub Actions）：PR のたびに、自動で確かめる

品質チェックの「道具の追加」の1つ目（[docs/quality-review.md](../docs/quality-review.md) の 5 章）。設定は `.github/workflows/ci.yml`。1本目（TaskManagement）の CI を、参考にした。

## CI とは
**CI（継続的インテグレーション）**：変更が入るたびに、テストなどを、自動で走らせる仕組み。人が、確認を忘れても、抜けても、機械が確かめる。GitHub では、**GitHub Actions** と呼び、`.github/workflows/` の中の、設定ファイル（YAML）に、手順を書く。

## 作ったもの
| ジョブ | 内容 | 結果（初回） |
|---|---|---|
| backend（pytest・ruff） | MySQL 8.4 を、CI の中で起動。`uv sync --locked` → `ruff check` → `ruff format --check` → `pytest` | 成功（pytest 173 件、ruff の指摘 0 件、整形済み 32 ファイル） |
| frontend（lint・test・build） | `npm ci` → `lint` → `format:check` → `test` → `build` | 成功（テスト 151 件） |

PR を作ったときと、main に入ったときに、動く。同じ PR に続けて push したときは、古い実行を止める。

## 学んだこと
- **手元と同じ確認を、GitHub の上で行う。** 新しい確認を作るのではなく、`CLAUDE.md` の「開発のコマンド」の表と、同じものを並べた。手元で通ったのに、CI で落ちる、を防ぐのが目的
- **CI の中に、使い捨ての MySQL を起動する（サービスコンテナ）。** テストは、本物の MySQL が要る。`services:` に、`mysql:8.4` を書くと、ジョブの間だけ、Docker で MySQL が起動し、終わると消える。**起動に時間がかかる**ので、つながる状態になるまで待つ設定（`--health-cmd`）を付ける。手元の `docker-compose.yml` と、同じ版（8.4）にそろえた
- **CI には、`.env` がない。** 手元では、パスワードなどを、`.env`（コミットしない）に書いている。CI には、そのファイルがないので、ジョブの `env:` で渡す。値は、**CI 専用のダミー**（テストが作って捨てる DB なので、本物の秘密ではない）。**本物の秘密は、CI の設定ファイルに書かない**
- **部品（uses）は、コミットの ID で固定する。** `uses: actions/checkout@3d3c42e…  # v7.0.1`。版の名前（`v7`）は、あとから別の中身に差し替えられることがある。ID なら、差し替えられない。出たばかりの版は避けた（`setup-uv` は、公開から約1か月たった v10.3.0 を選び、ID は、GitHub の API で調べた）
- **権限は、読み取りだけ**（`permissions: contents: read`）。秘密情報も使わない。OS は、**Ubuntu 24.04 に固定**。`ubuntu-latest` は、気づかないうちに新しい版に切り替わり、CI が壊れることがある
- **ロックファイルのとおりに入れる。** `uv sync --locked`、`npm ci`。ロックファイルとずれていたら失敗する。「手元と同じ版」を保てる
- **手元では、CI を動かせない。** だから、PR を作って、**PR の上で、初めて動かした**。ただし、その前に、設定ファイルの書き方を、検査の道具（actionlint）で確かめた（使い捨ての Docker で実行し、終わったらイメージも消した）。**書き方の誤りは、PR を作る前に、見つけられる**
- **緑の ✓ だけで、安心しない。** ログを見て、テストが本当に走ったこと（173 件、151 件）、整形チェックが通ったこと、注釈（警告）が 0 件であることを確かめた
- **Windows の手元では通るのに、Linux の CI では、落ちる穴**は、先に潰してあった。改行コード（Git の中は LF なので、Linux でも整形チェックが通る。前の PR で `endOfLine: auto` を入れた理由の1つ）。パスの区切りや、実行権限の問題は、今回の構成では、起きなかった
- **ジョブの名前（`name`）は、あとで「必須チェック」の設定が、頼る。** 変えると、GitHub 側の設定が、チェックを見つけられなくなる。ファイルに、注意を書いた

## 必須チェックの設定（Issue #115）
CI を作って、動作を確かめたあと、GitHub の「**ブランチの保護**」で、`main` を守る設定を入れた（ユーザーが承認）。

| 設定 | 値 |
|---|---|
| PR が必須 | する（`main` への直接の push は、できない。承認の人数は 0） |
| 必須のチェック | `backend（pytest・ruff）` と `frontend（lint・test・build）` が、どちらも成功しないと、マージできない |
| 管理者にも適用 | する（自分にも適用される） |
| 強制 push・`main` の削除 | 禁止 |
| 入れなかったもの | 「ブランチを最新にしないとマージできない」（1人開発では、面倒が増えるだけ） |

- **「守る」仕組みを、人の注意力に頼らない。** これまでは、「CI が ✗ のときは、マージしない」という約束を、人が守っていた。設定を入れると、**✗ のままでは、マージのボタンが押せない**。うっかりが、仕組みで防げる
- **管理者にも適用するのが、大事。** 適用しないと、自分だけは、ルールを破れてしまう
- **設定は、コマンドで読める・戻せる。** 設定前は「保護なし」だった。読むのは `gh api repos/…/branches/main/protection`、外すのは `gh api -X DELETE …`。**変える前に、今の状態を確かめ、戻し方を決めておく**。戻し方は、`CLAUDE.md` の 3.7 に書いた
- **落とし穴**：①CI 自体が壊れると（GitHub の障害や、設定のミス）、マージが止まる。そのときは、設定を一時的に外す ②`ci.yml` のジョブの `name` を変えると、必須チェックが「見つからない」状態になり、永遠に待つ。名前を変えるときは、設定も直す
- **設定を、あとから変えるときも、ユーザーに確認する。** GitHub の設定は、リポジトリの外（コードの外）にあり、PR のレビューを通らない。だから、適用前に、内容を見せて承認をもらった。適用後は、設定を読み直して、入ったことを確かめた
- 保護の設定の試験として、`main` へ、わざと直接 push することは、しなかった（保護が効いていなかった場合、本当に push してしまうため）。**次の PR で、必須チェックが表示されること**で確かめる

## やってみよう
1. GitHub で、PR（例：#114）を開き、「Checks」のタブで、`backend` のログを開く。`Run uv run pytest` のところで、テストの件数を見る
2. `.github/workflows/ci.yml` を開き、`uses:` の後ろの、長い英数字（コミットの ID）と、コメントの版の名前を、見比べる
3. `ci.yml` の `services:` と、`docker-compose.yml` の `db:` を、見比べる（同じ MySQL 8.4）
