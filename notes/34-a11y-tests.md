# アクセシビリティの自動検査（axe-core）

品質チェックの「道具の追加」の3つ目（[docs/quality-review.md](../docs/quality-review.md) の 5 章）。テストの中で、画面の部品を **axe-core**（アクセシビリティの検査の定番）にかけて、読み上げソフトやキーボードで使えない所を、機械に見つけさせる。

## アクセシビリティとは
目が見えない・見えにくい人が、音声で画面を操作したり、マウスを使えない人が、キーボードだけで操作したりできること。読み上げソフトが読むのは、見た目ではなく、HTML に書かれた**名前と役割**。名前がないボタンは、「ボタン」としか読まれない。

## 作ったもの
| 場所 | 中身 |
|---|---|
| `frontend/src/test-utils/a11y.ts` | 検査の関数（`a11yViolations`、`expectNoA11yViolations`）。違反があると、どの規則か・どの要素かを、失敗のメッセージに出す |
| `frontend/src/components/accessibility.test.ts` | 詳細モーダル・カテゴリー管理・テンプレート編集・一覧（`RequestTable`）の検査（23 件）。エラー表示・削除の確認・名前を直している最中など、画面の主な状態を、それぞれ検査 |
| 入れた部品 | `axe-core` 4.14.0（版を固定。公開から約1か月） |

画面のテストは、合計 200 件（元の 177 件＋23 件）。

## 測ったら、本当の違反が見つかった
| 部品 | 違反（axe の規則） | 直し方 |
|---|---|---|
| すべてのモーダル | モーダルに名前がない（`aria-dialog-name`）。読み上げソフトには、「ダイアログ」とだけ聞こえる | `v-dialog` に `aria-label` を付けた（「依頼の詳細」「カテゴリー管理」など。検査に出なかった、削除の確認や確認先の入力にも、同じ作りなので付けた） |
| 詳細モーダル | チェックリストのチェックボックスに、ラベルがない（`label`）。何のチェックか分からない | `aria-label` に、項目の名前を付けた |
| 一覧 | ステータスの札に、`aria-haspopup` があるのに、ボタンとして宣言されていない（`aria-allowed-attr`） | `role="button"` と、`aria-label`（「ステータス：確認待ち（押して変更）」）を付けた |
| 一覧 | 表の先頭の見出し（ドラッグの取っ手の列）が、空（`empty-table-header`） | 読み上げ用の文字（`visually-hidden`）を入れた |

どれも、**属性を足すだけで、見た目は変わらない**。直したあと、4つの部品すべてで、違反 0 件になった。前の PR（F3）で、Tab で開けるようにした、タイトルのボタンなどは、検査に通っていた。

## 学んだこと
- **自分では気づかない問題を、機械が見つけてくれる。** 「モーダルに名前がない」は、見た目では、まったく分からない。読み上げソフトで聞かないと気づけない。自動検査があると、**聞かなくても、見つかる**
- **「違反 0 件」は、検査が働いているときだけ意味がある。** 検査が壊れていれば、いつも 0 件になる。そこで、2つ確かめた。①**わざと違反を入れた部品**（名前のないボタン、ラベルのない入力欄、代わりの文字のない画像）を作り、検出できること。②**直した属性を、1つずつ外して**、テストが失敗すること（5 通りとも、検出できた）。外す前の状態は、バックアップから戻した
- **`aria-label` は、見えない名前。** 画面には出ないが、読み上げソフトが読む。`role="button"` は、「これは押せるボタン」という宣言。**押せる見た目の部品（札、アイコン）には、役割と名前が要る**
- **1つ直したら、同じ作りの所も、直す。** 検査が見つけたのは、3つのモーダルだけだったが、同じ `v-dialog` で作った、ほかのモーダル（削除の確認、確認先の入力）も、同じ問題を持っていた。**検査に出なかったものも、同じ作りなら、直す**。その状態を、検査に足した（削除の確認が出ているときなど）
- **自動検査の限界。** jsdom は、本物のブラウザではないので、次のものは検査できない。①**色のコントラスト**（見やすさ）。画面に描かないと、色が決まらないため。検査から外した（理由を、コードに書いた）。②**画面の配置**。③**読み上げソフトでの実際の聞こえ方**。自動で見つかる問題は、全体の一部。**聞こえ方は、人が確かめるしかない**（Windows のナレーター：Win + Ctrl + Enter）
- **ページ全体の決まりは、部品のテストでは外す。** 「ページに見出し1が1つある」などは、部品だけを描くテストでは、当てはまらない。外した規則と、理由を、コードに書いた（`DISABLED_RULES`）
- **手元に出ない出力が、ある。** 測定のために、テストの中の `console.log` で、違反を表示しようとしたが、手元では、出なかった（ただの試験用のテストでも、同じ。理由は、特定できていない）。CI では、出る。前に、手元では出ない警告が、CI にだけ出たのも、同じ事情かもしれない。**手元に出ない出力は、ファイルに書き出して読む**（今回は、測定の結果を、ファイルに書いた）。**「出ていない」ことの確認は、CI のログでも行う**
- **`npm audit`**：`axe-core` を足しても、指摘は増えなかった（本番の部品 0 件、全体 15 件のまま）

## やってみよう
1. `RequestTable.vue` の、ステータスの札の `role="button"` を、一時的に消して、`npm.cmd run test` を実行する。どのテストが、どう失敗するか見る（見たら、元に戻す）
2. `accessibility.test.ts` の「検査の道具が、働いていること」を読み、わざと違反を入れた部品を確かめる
3. Windows のナレーターをつけて、詳細モーダルを開く。「依頼の詳細」と読み上げられるか確かめる（自動検査では、できないこと）
