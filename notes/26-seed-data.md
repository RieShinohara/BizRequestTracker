# 初期データ（最初から入れておくデータ）

品質チェックの D1（[docs/quality-review.md](../docs/quality-review.md)）への対応。受け入れ条件「最初から、7つのカテゴリーと、それぞれの作業テンプレートが入っている」を、実装した。

## 何が問題だったか
マイグレーション（0001）は、**表（入れ物）を作るだけ**で、中身は入れていなかった。手元の開発用 DB には、手で作ったカテゴリーがあったので、気づかなかった。**新しい DB（AWS）で始めると、カテゴリーが0件**で、カテゴリーが必須の依頼を、1件も作れない。

## 作ったもの
| 場所 | 中身 |
|---|---|
| `backend/migrations/versions/0002_seed_categories.py` | 7つのカテゴリーと、各テンプレート（計 57 項目）を入れるマイグレーション |
| `backend/tests/test_seed_categories.py` | 初期データのテスト（カテゴリー7つ・項目数・順番）と、すでにデータがある DB でも壊れないことのテスト |

## 学んだこと
- **初期データも、マイグレーションで入れる。** `uv run alembic upgrade head` の1回で、表と初期データがそろう。手順書の「あとで、このスクリプトも実行する」が要らず、実行し忘れが起きない
- **何度実行しても、安全にする（冪等：べきとう）。** 「同じ名前のカテゴリーがあれば、何もしない」作りにした。開発用 DB には、すでに4つのカテゴリーがあったが、**項目も依頼も、そのまま残り、足りない3つだけ**が増えた。あとで、管理画面でテンプレートを直しても、マイグレーションを再実行して、上書きされることはない
- **`downgrade`（元に戻す）では、何も消さない。** 消すと、依頼が使っているカテゴリーや、ユーザーが直した内容まで、消えてしまうため。「元に戻せる」ことと、「データを守る」ことの、どちらを優先するかを、決めて、コメントに書いた
- **マイグレーションの中に、データを直接書く。** アプリのモデルや設定ファイルを読まない。マイグレーションは、「その時点の記録」なので、あとでアプリが変わっても、結果が変わらないようにする
- **テストが、初期データの影響を受けた。** テストは、マイグレーションで表を作っているので、初期データも入る。すると、「テンプレート項目が0件」と数えるテストや、「動画」という名前でカテゴリーを作るテストが、失敗した（3件）。**テストを、初期データに頼らない形に直した**（そのカテゴリーの項目だけを数える、名前を変える）。「表が空」を前提にしたテストは、データが入ると壊れる
- **「すでにデータのある DB」は、使い捨ての DB で試す。** テストの中で、専用の DB を作り、先にユーザーが作ったカテゴリー（項目1つ）を入れてから、`upgrade` する。上書きされないこと、もう一度実行しても増えないことを確かめ、終わったら DB を消す。`stamp` で「0002 は、まだ実行していない」ことにして、再実行できる

## やってみよう
1. `docs/functional-requirements.md` の 7 と、`0002_seed_categories.py` の `SEED` を見比べる（項目の順番が同じか）
2. `uv run pytest tests/test_seed_categories.py -v` を実行する（3件成功）
