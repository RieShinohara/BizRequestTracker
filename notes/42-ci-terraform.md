# CI に、Terraform のチェックを足す

Issue #143。Terraform（AWS の構成のコード）の点検を、手元で実行するだけでなく、PR のたびに自動で行うようにした。`.github/workflows/ci.yml` に、3つ目のジョブ `terraform（fmt・validate・tflint・trivy）` を足した。**AWS には、つながない**（秘密も、認証情報も使わない）。

## 4つの道具の役割
| 道具 | 見るもの | たとえ |
|---|---|---|
| `terraform fmt -check` | 書き方の整形（字下げ、揃え方） | 文書の体裁 |
| `terraform validate` | 文法と、部品のつじつま（存在しない変数を使っていないか） | 誤字・脱字の校正 |
| tflint | Terraform 特有の、良くない書き方（型がない変数、使っていない宣言、AWS の値の間違い） | 校閲 |
| trivy | セキュリティの弱点（入口が全世界に開いている、など） | 防犯の点検 |

## 学んだこと
- **道具の版は、固定する。** `hashicorp/terraform:1.16.6`、tflint `v0.65.0`、trivy `0.76.1`、tflint の AWS プラグイン `0.40.0`。固定しないと、道具が新しくなった日に、何も変えていないのに、CI が失敗する。上げるときは、手元で確かめてから
- **外部の「部品（アクション）」を増やさず、使い捨ての Docker で動かした。** 手元で動かした手順と、ほぼ同じ形になる。第三者が作った部品を増やすと、差し替えのリスクも増える
- **「成功」は、道具が働いているときだけ意味がある（空振りの罠）。** 手元で確かめるとき、Git Bash の `$PWD`（`/c/Users/...` の形）を、Docker に渡したら、**空のフォルダを調べて、「成功」と出た**。空のフォルダでも、fmt・validate・tflint は、成功する。**`$(pwd -W)`（`C:/Users/...` の形）に直して、中身が見えているか（`ls`）を確かめてから、やり直した**。ノート 34（「違反 0 件」は、検査が働いているときだけ意味がある）と同じ
- **わざと壊して、失敗するか確かめた。** 整形を崩す → fmt が失敗。存在しない変数 → validate が失敗。型のない変数 → tflint が失敗。SSH の入口を `0.0.0.0/0` → trivy が HIGH で失敗（AWS-0107）。**4つとも、検出できた**
- **trivy の `--ignorefile` は、絶対パスで書く。** 相対パスだと、「ファイルが見つからない」と言われた
- **スイッチ（`create_database`）が false のときは、RDS を調べない。** そのため、trivy は2回実行する（false のときと、true にしたときは、ダミーの値で）

## やってみよう
1. PR の Checks で、`terraform` のジョブを開いて、4つの手順（fmt・validate・tflint・trivy）が、順に動いたことを見る
2. `terraform/security_groups.tf` で、わざと入口を `0.0.0.0/0` に書き換えて（コミットしない）、手元で trivy を動かし、`AWS-0107` が出ることを確かめる
