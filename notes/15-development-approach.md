# 進め方の比較：機能ごとに作る／API を先に全部作る

## きっかけ
1本目（TaskManagement）は、機能（CRUD）ごとに「API 設計 → バックエンド → フロントエンド」を1セットずつ作った。2本目（BizRequestTracker）は、API を全17本先に作り、そのあとで画面を作る進め方になった。「どちらが良いのか」を整理した。

## 2つの進め方
| | 機能ごとに作る（1本目） | API を先に全部作る（2本目） |
|---|---|---|
| 良い点 | 1つ作るたびに画面で動かせるので、早く気づける。設計の間違いを、小さいうちに直せる | 全体を見て設計できるので、API の作りに一貫性が出る。バックエンドに集中でき、テストもまとめて書ける |
| 悪い点 | 設計が後回しになるので、あとの機能で、前の API を作り直すことがある。API と画面を行き来する手間がかかる | 画面とつなぐのが遅くなり、「画面で使うと不便」という発見も遅れる |
| 向く場面 | 要件があいまいで、作りながら決めていくとき | 要件・画面設計・プロトタイプが固まっているとき |

## 今回、API 先行が合った理由
- 要件定義、データ設計、プロトタイプ、API 設計を、先に終えていた
- 使う人が1人で、画面の動きも決まっていたので、設計がぶれにくかった

## 現実的には中間もある
設計は全体で行い、実装は小さく区切って、画面とつなぐ。今回も、画面は「一覧の表示」から1つずつ作る。API の不足が見つかったら、バックエンドに戻って直す（その場合も、先に Issue を作る）。

## 気づいたこと
- どちらが正解ということはなく、**設計がどれだけ固まっているか**で選ぶ
- どちらの進め方でも、「API → 画面は別々の Issue・PR」というルールは同じ
- 両方を経験できたことが、学習としての収穫
